# Governance

Good work needs clear ownership, understandable decisions, and a review process people can follow.

## Scope

This document governs the `uslusoftware/uslusoftware` profile repository and its documentation, visual assets, and collaboration templates. Other repositories may adopt these guidelines explicitly or define their own.

This repository does not automatically configure policies, permissions, or templates across the account. Shared community defaults belong in a separate public `.github` repository.

## Roles and responsibilities

| Role | Responsibility |
| :--- | :--- |
| **Account owner** | Holds final responsibility for repository access, maintainer appointments, public representation, and unresolved decisions. |
| **Maintainers** | Coordinate work, review contributions, check accuracy, and merge changes within their assigned responsibilities. |
| **Contributors** | Work within an agreed scope, explain their changes, and provide suitable validation. |

The owner is the holder of the `uslusoftware` account. Maintainer responsibilities must be assigned explicitly; submitting a contribution does not grant repository access or approval authority. GitHub permissions determine who can perform each action.

## Contribution model

Work is primarily coordinated within the team. External contributors should first open a non-sensitive proposal or contact [usluyapimorg@gmail.com](mailto:usluyapimorg@gmail.com). A maintainer should confirm scope before implementation starts.

Agreeing to discuss a proposal does not commit the team to accepting or delivering it. An invitation to contribute applies to the agreed work.

## Making decisions

1. **Describe the need.** Explain the problem, intended outcome, and affected content or behavior.
2. **Agree on scope.** A maintainer confirms the direction, review needs, and any restrictions on public discussion.
3. **Review the change.** Use a pull request with enough context and validation for another person to assess it.
4. **Record the outcome.** Keep the decision and its reasoning in the issue or pull request. Summarize private decisions publicly only when doing so is appropriate.

Small editorial corrections can go directly to a pull request. Changes to brand positioning, contact details, public service descriptions, governance, or security reporting require the account owner's approval.

We prefer agreement after discussion. If a decision remains unresolved, the account owner makes the final call and records the rationale. A reviewer with a personal conflict should disclose it and involve another maintainer or the owner.

## Review and merge expectations

- Keep changes focused and explain their purpose.
- Request review from a maintainer familiar with the affected area. Seek a second person's review when available; the author should not present self-review as independent approval.
- Check factual claims, links, and visual presentation before merging public-facing changes.
- Resolve substantive review concerns or document why the owner accepts a remaining tradeoff.
- Use the repository's actual checks and review controls. These guidelines alone do not enable branch protection or required reviews.

If the owner must merge without an independent reviewer, record the reason and the validation performed in the pull request. Avoid treating an exception as the normal review path.

## Access and confidential information

Grant repository access according to the work a person needs to perform. Review access when responsibilities change. Client materials, production credentials, mailbox contents, and internal business information belong in approved private channels.

## Urgent corrections

An authorized maintainer may make the smallest necessary correction to remove exposed information, repair a harmful link, or address an immediate security concern. Record a sanitized explanation and obtain owner review afterward. Treat exposed credentials as compromised; removing a file is only one part of the response.

## Updating these guidelines

Propose changes through a pull request. Explain what changes in practice and why. The account owner approves governance changes before they take effect.
